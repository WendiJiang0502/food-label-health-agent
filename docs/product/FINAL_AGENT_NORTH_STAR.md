# 食品标签解释与替代品 Agent：最终目标文档

> 文档性质：Product & Agent North Star / 项目最终目标基准
> 目标市场：中国大陆优先，后续扩展英文与其他法域版本
> 适用对象：产品设计、Agent 开发、RAG 建设、规则引擎、前端、评测与安全审查
> 重要说明：本文描述最终产品目标，不代表所有能力已经实现。

## 1. 一句话定义

食品标签解释与替代品 Agent 是一个面向预包装食品的多模态智能 Agent：用户拍摄食品标签后，系统识别并确认标签事实，结合用户的过敏原、饮食偏好和营养限制，调用确定性规则、官方标准 RAG 与产品检索工具，解释配料和包装声称、标记个人风险，并推荐经过约束复核的替代品。

面向普通用户的简短表达：

> 拍下食品标签，看懂配料、发现风险、找到更合适的选择。

## 2. 产品要解决的问题

用户面对食品包装时，往往无法可靠回答以下问题：

- 配料表中的陌生名称和食品添加剂是什么；
- 过敏原是否以别名、衍生物或复合配料的形式出现；
- “无糖”“0 蔗糖”“低糖”“不添加糖”“零添加”是否为同一概念；
- 包装声称与配料表、营养成分表是否一致；
- 某项判断依据的是哪一条中国官方标准；
- 当前食品不满足个人约束时，有哪些证据更完整的替代品；
- 标签模糊、法规证据不足或商品配方不完整时，哪些结论不能确定。

本产品不只是 OCR，也不只是聊天机器人。它要完成从图片事实到个性化、可追溯决策的完整链路：

```text
食品标签图片
→ 标签事实
→ 用户确认
→ 配料与营养结构
→ 个人约束判断
→ 官方标准证据
→ 通俗解释
→ 替代品搜索与复核
→ 最终安全回答
```

## 3. 最终用户体验

典型用户问题：

> 我对牛奶过敏，也想控制钠。这个食品可以吃吗？“0 蔗糖”是什么意思？如果不适合，请帮我找替代品。

最终 Agent 应自主完成：

1. 接收一张或多张食品包装图片；
2. 检查图片质量并调用 OCR；
3. 提取配料、过敏原声明、营养成分和包装声称；
4. 对低置信度、漏行和表格错配进行阻断；
5. 让用户确认关键标签事实；
6. 将确认后的配料解析为标准化、可追溯的结构；
7. 读取本次会话或用户授权保存的个人约束；
8. 使用确定性规则引擎匹配过敏原、饮食模式和营养限制；
9. 判断需要检索哪些官方标准和配料知识；
10. 通过混合 RAG 检索当前法域和日期适用的官方条款；
11. 解释添加剂、营养指标与包装声称；
12. 必要时检索候选替代品；
13. 对每个候选商品重新执行标签完整性和个人约束检查；
14. 通过最终安全门生成带证据、风险等级和未知项的回答。

## 4. 最终系统架构

系统采用五层架构。

### 4.1 感知层

职责：将图片转换为可核对的标签证据。

包含：

- 图片格式与真实性校验；
- 模糊、反光、倾斜和局部清晰度检查；
- 中国版主 OCR 与本地备用 OCR；
- 配料区域定位；
- 营养表结构恢复；
- 字段级置信度、坐标和原始证据保留。

OCR 只提供候选事实，不负责健康判断。

### 4.2 事实层

职责：把用户确认后的标签文字转换为稳定的领域数据。

包含：

- Human-in-the-loop 标签确认；
- 配料切分与括号树解析；
- 复合配料关系；
- 配料别名与标准名；
- 食品添加剂识别；
- 营养单位和计量口径规范化；
- 包装声称结构化；
- 原文位置和用户修正记录。

所有规范化结果必须能够追溯到确认后的原文。

### 4.3 安全与知识层

职责：产生确定性风险结果，并提供官方证据。

包含：

- 中国版过敏原规则引擎；
- 不耐受、饮食偏好与主动回避规则；
- 营养限制规则；
- 添加剂知识库；
- 中国食品标准混合 RAG；
- 法域、发布日期、生效日期和失效日期过滤；
- 标签、配料、营养值和包装声称一致性检查。

硬性风险由规则决定，LLM 只负责解释，不能修改风险等级。

### 4.4 Agent 编排层

职责：根据当前问题和状态选择工具、管理流程并处理失败。

包含：

- LangGraph 状态机；
- 受约束的 ReAct 工具循环；
- 单个模块化 MCP Server；
- 工具调用预算与最大循环次数；
- 状态持久化和断点恢复；
- 上下文构建与压缩；
- 短期会话记忆和经授权的长期用户记忆；
- Agent 轨迹、证据和审计事件。

### 4.5 产品决策层

职责：把事实、规则和官方证据组织成用户可执行的回答。

包含：

- 是否适合当前用户；
- 命中的成分和原因；
- 风险等级与未知项；
- 配料和添加剂解释；
- 包装声称解释；
- 官方依据；
- 替代品及比较；
- 医疗边界和必要警告。

## 5. LangGraph 最终工作流

主流程必须是受控状态机，而不是一个无限自由对话的 LLM。

```text
validate_input
→ extract_label
→ confirm_label（必要时）
→ normalize_label
→ evaluate_safety
→ retrieve_regulations
→ interpret_label
→ search_alternatives（必要时）
→ revalidate_alternatives
→ final_safety_gate
→ completed / needs_confirmation / blocked
```

强制原则：

- 未确认的关键 OCR 字段不能进入健康解释；
- 过敏原规则不能被跳过；
- 法规解释必须绑定适用法域和日期；
- 替代品必须经过与原食品相同的约束复核；
- 所有完成路径必须经过最终安全门。

## 6. ReAct 在本项目中的作用

ReAct 用于处理“下一步应该调用什么工具”的动态决策，而不是替代确定性安全规则。

标准循环：

```text
Reason about the next required evidence
→ Act by calling one approved tool
→ Observe structured tool output
→ Update AgentState
→ Decide the next tool or stop condition
```

示例轨迹：

```text
用户上传图片并询问乳过敏风险
→ analyze_label_image
→ request_label_confirmation
→ normalize_food_label
→ evaluate_user_constraints
→ search_food_regulations
→ explain_ingredient
→ final_safety_gate
```

ReAct 可以决定：

- 是否需要补拍或请求用户确认；
- 当前问题需要检索哪类标准；
- 是否需要解释某个添加剂；
- 是否需要执行一致性检查；
- 是否需要搜索替代品；
- 工具失败后是否使用安全的备用工具。

ReAct 不可以决定：

- 将未确认 OCR 当作事实；
- 覆盖规则引擎的 `avoid` 结果；
- 猜测缺失的营养数值；
- 在没有官方证据时宣称符合法规；
- 把“未发现”表述为“绝对安全”。

## 7. MCP 工具目标

最终单体模块化 MCP Server 至少提供以下工具：

| 工具 | 作用 |
|---|---|
| `analyze_label_image` | OCR、字段定位、表格恢复和证据质量检查 |
| `normalize_food_label` | 规范化配料、营养成分、过敏原声明和包装声称 |
| `evaluate_user_constraints` | 使用确定性规则评估过敏、饮食和营养硬约束 |
| `search_food_regulations` | 检索适用日期内的中国官方标准条款 |
| `explain_ingredient` | 基于知识库与法规证据解释配料或添加剂 |
| `interpret_label_claim` | 解释无糖、低糖、不添加等包装声称 |
| `verify_label_consistency` | 交叉检查配料、营养表和包装声称 |
| `find_alternative_products` | 在硬约束过滤后检索候选替代品 |
| `compare_food_products` | 在统一计量口径下比较产品 |
| `revalidate_alternatives` | 对候选商品重新运行完整安全规则 |

每个工具必须返回结构化结果、证据 ID、未知项和错误类型，不能只返回自然语言。

## 8. 混合 RAG 目标

### 8.1 数据源原则

健康与合规解释优先使用：

- 国家卫生健康委员会；
- 国家市场监督管理总局；
- 国家标准全文公开系统；
- 现行食品安全国家标准；
- 官方标准问答和正式解释材料。

非官方内容只能作为低等级补充，不能支持安全关键结论。

### 8.2 文档处理

文档必须按照标准结构切分，而不是机械定长切分：

- 标准编号；
- 章节和条款；
- 定义；
- 限量或阈值表格；
- 食品类别；
- 附录；
- 生效和失效日期。

每个 chunk 保存来源、法域、日期、章节、链接、文档哈希和权威等级。

### 8.3 检索链路

```text
问题与当前状态
→ 查询改写
→ BM25/全文检索
→ Embedding 向量检索
→ 结果合并与去重
→ 法域和日期过滤
→ 权威等级过滤
→ Reranker
→ 条款级证据包
→ Grounded generation
```

BM25 负责标准编号、添加剂名称和精确术语；Embedding 负责自然语言、同义表达和语义问题。最终排序同时考虑相关性、官方权威性、时效性和条款完整性。

### 8.4 生成约束

- 回答中的法规结论必须引用检索证据；
- 找不到适用证据时必须输出 `unknown`；
- 模型预训练记忆不能替代官方检索；
- 过期标准不能与现行标准混用；
- 引用必须能定位到具体条款，而不是只给文档首页。

## 9. 上下文工程

Agent 不应把所有历史消息和所有文档塞入一个 Prompt。上下文分为四层：

### 当前任务上下文

- 用户当前问题；
- 当前食品；
- 法域与适用日期；
- 当前工作流阶段；
- 尚未解决的未知项。

### 已确认事实上下文

- 用户确认后的配料；
- 营养成分；
- 过敏原声明；
- 包装声称；
- 对应原文证据位置。

### 用户约束上下文

- 过敏；
- 不耐受；
- 饮食模式；
- 主动回避项；
- 营养限制；
- 约束严重程度和来源。

### 检索证据上下文

- 与当前问题直接相关的官方条款；
- 来源、章节和日期；
- 检索分数和权威等级；
- 证据间冲突与缺口。

上下文构建器只向每个节点提供完成该节点所需的信息，并保留 Token 预算。

## 10. Agent 记忆

### 短期记忆

保存当前分析会话中的：

- 已确认标签；
- 用户本次声明的约束；
- 已调用工具；
- 已检索证据；
- 未知项和待确认项。

### 长期记忆

仅在用户明确授权后保存：

- 长期过敏原；
- 饮食偏好；
- 营养限制；
- 回答形式偏好；
- 用户确认过的标签修正历史。

长期记忆必须可查看、修改、删除和撤销授权。历史商品标签不能永久视为当前配方，复用时必须提示重新核对。

不得将模型的内部思维链、未经确认的健康推断或无明确用途的全部对话保存为长期记忆。

## 11. 确定性风险模型

统一风险等级：

| 等级 | 含义 |
|---|---|
| `avoid` | 已确认标签明确违反用户硬约束 |
| `caution` | 存在“可能含有”、交叉污染、证据歧义或需要专业确认 |
| `compatible` | 在当前已确认标签和规则范围内未发现冲突 |
| `unknown` | 标签、规则映射或官方证据不足 |

`compatible` 不能解释为医学意义上的绝对安全。

每个风险结果至少包含：

```json
{
  "risk_level": "avoid",
  "constraint": "milk",
  "matched_text": "乳清蛋白",
  "canonical_ingredient": "whey_protein",
  "reason_code": "DIRECT_ALLERGEN_DERIVATIVE",
  "explanation": "配料中明确出现乳来源成分",
  "evidence_ids": ["label.ingredients.2"]
}
```

## 12. 替代品推荐原则

替代品推荐是约束满足和证据验证问题，不是基于商品名称的语言联想。

流程：

1. 将用户要求转换为硬约束和软偏好；
2. 检索同类商品候选；
3. 排除缺少可靠标签证据的商品；
4. 排除命中过敏原或饮食硬约束的商品；
5. 将营养数值转换为可比较口径；
6. 检查产品类别和使用场景是否可替代；
7. 对候选商品重新运行安全规则；
8. 按约束满足度、证据质量和营养偏好排序；
9. 展示推荐理由、证据和仍需核对的事项。

任何候选商品只要标签证据不足，就不能被描述为“安全替代品”。

## 13. 最终回答结构

最终回答优先回答三个问题：

1. 当前是否适合用户；
2. 命中了什么成分或规则；
3. 判断依据是什么。

推荐结构：

```text
结论：避免 / 谨慎 / 当前未发现冲突 / 无法确定

关键原因：
- 命中成分
- 对应用户约束
- 标签中的证据位置

标签解释：
- 配料或添加剂的通俗解释
- 包装声称的准确含义

官方依据：
- 标准名称、条款、适用日期和链接

替代选择：
- 经过约束复核的候选商品
- 主要差异和仍需核对事项

未知与限制：
- 缺失标签、证据不足或法规不确定性
```

回答必须简洁优先，允许用户继续追问深入解释。

## 14. 安全边界

- 产品提供食品标签信息整理与解释，不提供医疗诊断或治疗；
- 严重过敏、儿童、孕期、慢性疾病等高风险场景应建议咨询医生或营养专业人员；
- OCR 不得静默补字；
- LLM 不得猜测缺失数字；
- 过敏原硬规则优先于自然语言生成；
- 官方来源优先于模型记忆和非官方文章；
- 无证据时必须承认未知；
- 替代品必须重新验证；
- 最终安全门不能被 ReAct 或生成模型绕过。

## 15. 非目标

最终产品也不应承担以下职责：

- 诊断食物过敏或疾病；
- 根据一次扫描判断长期健康结果；
- 宣称某种添加剂对所有人“有毒”或“绝对安全”；
- 在没有完整标签时保证商品符合用户约束；
- 使用非官方信息代替法规依据；
- 为展示多 Agent 而无意义地增加模型角色；
- 暴露用户图片、密钥、健康偏好或内部思维链。

## 16. 多 Agent 演进原则

第一版优先采用：

```text
一个 LangGraph Orchestrator
+ 多个确定性或检索型 MCP 工具
```

只有在上下文隔离、并行研究或独立复核确有收益时，才拆分：

- Label Agent：标签事实和规范化；
- Safety Agent：过敏原与饮食约束；
- Regulation Agent：官方标准研究；
- Alternative Agent：商品搜索与复核；
- Reviewer Agent：证据完整性和最终回答检查。

多 Agent 的目标是专业上下文隔离和独立验证，而不是让多个模型自由讨论。

## 17. 评测体系

### OCR 与事实层

- 字符错误率 CER；
- 配料 token precision/recall；
- 配料区域边界准确率；
- 营养素—数值对齐准确率；
- 单位准确率；
- 低质量图片阻断召回率。

### 规则引擎

- 明确过敏原召回率；
- 严重漏报率；
- 别名和衍生物覆盖率；
- `avoid/caution/compatible/unknown` 一致性；
- 规则结果证据可追溯率。

### RAG

- Retrieval Recall@K；
- 条款相关性；
- 法域和日期过滤准确率；
- 引用正确率；
- Groundedness；
- 无证据时的正确拒答率。

### Agent

- 工具选择准确率；
- 工具调用参数准确率；
- 状态转换正确率；
- 不必要工具调用率；
- 循环和超时率；
- 安全门绕过率；
- 完整任务成功率；
- 轨迹可审计性。

### 替代品

- 硬约束违反率；
- 标签证据覆盖率；
- 营养口径一致性；
- 候选重新验证率；
- 推荐理由可追溯率。

## 18. 最终完成标准

只有同时满足以下条件，才能称为完整食品标签 Agent：

- 图片到确认标签的流程可用；
- 配料和营养结构能够追溯到原文；
- 用户约束能够进入统一 AgentState；
- 确定性过敏原规则真实运行；
- 官方标准混合 RAG 真实运行；
- ReAct 能根据问题选择 MCP 工具；
- LangGraph 能执行完整安全路径；
- 上下文按节点构建，而不是无限堆叠；

- 最终回答包含证据、风险和未知项；

## 21. 项目北极星

每次增加功能前，都应回答以下问题：

1. 它是否让 Agent 更接近“从标签证据到个性化决策”的完整闭环？
2. 它属于感知、事实、安全知识、Agent 编排还是产品决策层？
3. 它是否保留了从结论回到标签或官方条款的证据链？
4. 它是否会让 LLM 越过确定性规则或医疗边界？
5. 它是否有可以自动评测的成功标准？

最终产品的核心不是“模型能说多少”，而是：

> Agent 能否在证据不足时停下来，在事实确认后正确调用工具，在个人约束下给出可追溯、可解释且不越界的食品选择建议。
